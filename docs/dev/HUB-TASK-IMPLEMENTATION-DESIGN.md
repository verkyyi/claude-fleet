# Hub 任务减法：最终交互与完整调整方案

实施中 · 2026-10-23 · Subagent 与列表已发布，推进唯一执行绑定与停止

[查看最终交互原型](task-list-prototype.html) · [界面规格](TASK-LIST-DESIGN.md) · [前期研究与原生能力来源](HUB-TASK-SIMPLIFY.md)

## 先看结论

Fleet 只管理「你的任务在哪里运行、如何连接、怎样停止」。任务如何拆解、使用多少原生 Subagent、怎样完成工作，由负责该任务的 Coding Agent 决定。

最终只保留 Task 一种工作对象；没有管家、协调者、Parent–Child、EPIC、Batch 或专属 driver。每个 Task 同时最多绑定一个顶层 Coding Agent Session，历史会话仍可查看与恢复。结果是产物和事件，不是任务的「已完成」终态。

这份方案借鉴 EPIC DESIGN 的两层阅读方式：先看用户收益、范围与目标，再展开实施细节。这里的工作切片是文档组织，不创建 EPIC、父任务、子任务、集合或协调 Agent。本轮已进入实施；下面的目标验收尚不能视为全部上线。

### 执行控制：已发布的基础与当前接线

Hub Store 事务与节点持久停止栅栏已通过 [PR #5360](https://github.com/verkyyi/claude-fleet/pull/5360) 发布。派发、原生启动、输入、唤醒与停止接线已随 [PR #5362](https://github.com/verkyyi/claude-fleet/pull/5362) 发布为 `07d4dc0c5`；正式 CI 全绿，Hub、stable 和两处受控执行登录的安装关键文件均已核验。**节点尚未声明 `task_execution_v1` 能力，普通派发默认不启用新协议；不能据此宣称全链路唯一执行或完整 Task stop 已上线。** 旧会话不自动接管，历史 `@dispatch` 也不会变成恢复时的在线依赖。

| 代码职责 | 约束 |
| --- | --- |
| Hub 授权与 operation 入账 | 同事务占用 Task 的端点和 operation；尚未填入 worker 也算占用。不同幂等键不能取得第二个绑定；已有旧启动记录不能在缺少退出证明时自动接管。 |
| 真实会话领取 | 节点分配真实 Session FID 后领取；Task FID 是任务身份，不冒充 Session FID。绑定不因超时、普通启动结果或 inventory 消失释放。 |
| Hub 停止意图 | 在网络请求前持久保存，推进 `generation`，保留旧绑定及其 attempt/generation。重复请求返回同一个停止 operation；旧取消和迟到回执不能覆盖它。 |
| 节点持久栅栏 | 复用 `control/state.sqlite3`。停止先提交，不等待启动锁；旧快照不能清除停止。已存在的执行绑定，即使收到更高代次，也不能在没有退出证明时替换。 |
| 启动临界区 | Task 级短锁仅覆盖本地检查、创建与登记，网络请求在锁外。停止可以在区间内提交；创建中的进程仍须由接入方负责追踪和终止，单次检查不等于已经停止。 |
| Codex 进程清理 | guardian 作为仍存活的私有进程组锚点，主 app-server 先退出也清理同组后代；不对已回收 PID/PGID 盲目发信号。自行创建新 session/group 的后代仍不在这项证明范围内。 |

operation 中固定的 `control_version=1` 仅标识新协议，与历史归档字段区分；它不是第二个递增控制时钟。Hub 与节点共用快照字段：`task_ref/task_fid/generation/binding_generation/attempt_id/operation_id/execution_endpoint/execution_owner/cancel_request`。其中 `binding_generation` 来自原始 attempt，只是保留旧执行的代次。

接线必须按以下顺序验收：

1. LOCAL 与 REMOTE 派发都取得同一事务授权；节点能力明确声明后才可选择该协议。仅明确的未执行拒绝可换机重试，超时或查询不到不能释放绑定。
2. 节点领取真实会话身份；wrapper 的每次原生启动及 restore、transfer/rollback、历史恢复、停放接回都检查同一持久栅栏。
3. 停止先持久接受，再撤销旧输入、唤醒与原生计划，并终止已登记执行域。重连先同步停止，再恢复工作；复用原 operation ID。
4. 匹配原绑定、attempt 和进程出生身份的退出证明到达后，才允许用户明确继续或切换。未知结果保留证据，不能虚报停止或启动第二份。
5. 覆盖并发开始/停止、离线重连、主进程先退出与后台后代、节点重启的端到端演练后，再接两端完整 Task 停止，最后退役 Parent/EPIC/driver 写入和消费者。

### 恢复保护与显式接续基础（#5363 已发布）

恢复窗口在启动 wrapper 之前写入真实 Session FID，并在恢复快照中保留显式执行协议元数据。元数据损坏、身份写入失败或本地执行账本缺失时拒绝启动，不能降级为旧会话绕过停止；历史不受控会话保留原恢复路径。

节点新增只读 `native_session` 退出证明函数：匹配已持久保存的停止快照，核验已登记原生根组件的 PID 与内核出生标记，显示时区变化不视为 PID 复用。匹配身份的僵尸进程可证明已退出；历史启动中断只核验已登记组件，缺失 child 的启动仍保持未确认。当前原生会话登记不完整或内核信息读不到也保持未确认。Store 复用 operation 保存不可变的会话退出回执；核对原 Task、Session、端点、attempt、启动和停止操作后才释放绑定。显式接续用新的幂等键和停止之后的新 generation；旧回执重放不能清除新绑定。释放绑定后重复停止仍返回原结果，接续之后的旧停止请求不能影响新绑定。历史 Session 身份仍保留，不能改投另一 Task。

恢复保护、重连同步与退出回执 HTTP 接口已发布；节点回执自动提交 #5366 已合并、待发布，范围见下。**用户继续/换 Agent API、节点新授权接续与原生持久计划撤销尚未完成。** 不能据此启用 `task_execution_v1` 或声称用户停后接续已交付。默认能力保持关闭，普通会话不被自动接管。


### 重连同步接线（#5364 已发布）

节点每个登录的连接收到 Welcome、启动消息读取后，异步读取已有的停止快照；失败由既有心跳重试。同步不阻塞停止消息、查询或同机其他登录，连接断开会取消本次同步 helper，HTTP 子进程按自身超时收尾；这不承诺所有子进程瞬时退出。这里的运行／成功标记只防止同一连接重复发请求，不是 Task 状态，也不授予执行权。

受控会话领取前先同步停止，再分配 Session FID；恢复、输入与唤醒的授权刷新也先同步停止，重查本地记录后才读取单任务授权。同步只导入停止，不把活跃快照变成新授权，不清除历史停止记录。认证请求均在数据库事务和执行锁之外。旧未受控会话不因这条路径联网。

本地 `execution_sync` 标记仅表示支持同步命令，不是 Hub 的 `task_execution_v1` 能力。同步成功表示停止指令已落本地，不能冒充原生进程已经退出。退出回执提交见下一节；显式继续、原生计划与独立队友处理仍需接线与验收，默认执行能力继续关闭。

### 用户明确继续与换 Agent 的 Hub 接口（本切片，尚未全链路启用）

`POST /v1/fleet/tasks/<ref>/continue` 只接受任务本人，以原停止操作、当前 generation 与幂等键表达一次明确继续；可指定 Claude/Codex，省略时继承上一段不可变启动记录中的 Agent。事务要求原生退出回执已经接受、原执行绑定已释放，并保持原节点与工作环境；并发不同请求只能产生一个新授权，同 key 重放返回原操作，不重复派发。Task 的初始请求和历史不改写。

节点只收到 `continuation={version:1,exit_operation_id}`，不接收新 Parent 或恢复旧输入队列。认证的 `execution/start` 读取当前启动事实，并从退出回执精确取得原 `source_start`；本机直接启动没有节点远端派发日志时也能核验原 Agent、仓库和工作环境。原有执行快照字段不增加。节点断连、缺少接续能力、旧停止证明或错误所有权均拒绝，不自动改派其他节点。

此片定义并检查 `task_continuation_v1`，尚无节点声明该能力，用户界面和真实启动器仍待接线。旧 Outcome 对明确继续的限制、未领取启动的停止证明、原生持久计划与独立队友停止另片处理，不能据此宣称所有 Task 均可继续或完整停止已交付。

### 节点退出回执提交（本切片，待发布）

受控 stop 清理结束后独立尝试证明顶层原生会话退出，即使 tmux 窗口已不存在也不跳过。provider 只从当前完整原生组件登记确定；未领取、未启动、缺少登记、活进程或无法确认内核身份均保持未证明。首次完整 proof 和固定幂等键在原 stop 的 `operations.result.native_exit_receipt.payload` 中原子保存，再经既有节点认证提交；网络不持有数据库、admission、FID 或清理锁。并发结果更新、stop 重投和进程崩溃不会替换原包，公开 operation 只显示确认摘要，不携带大包。退出确认不冒充窗口清理成功，原 cleanup 状态保留。

Hub 接受后即使响应丢失，也不依赖再次投递 stop：既有节点 heartbeat/reconnect 异步扫描同一 journal，默认每轮最多 8 条、12 秒预算；证明保存后按剩余预算发送，网络最长 8 秒，连接内至少间隔 30 秒；外层 helper 受 20 秒取消边界约束。重试只提交原包，不重做 stop、不清除栅栏，也不触碰后来绑定。`execution_exit_retry` 仅是本地命令探针，不是执行能力或新的 Task 状态。仍未提供未领取任务的退出证明、新授权接续、resume API 或原生计划取消，`task_execution_v1` 保持关闭。

### 节点退出回执 API（#5365 已发布）

节点退出回执 API 已发布：仅现有节点认证入口可提交 `native_session` 证明，owner 与 endpoint 从认证身份派生；Hub 校验原生组件登记的传输结构，Store 核验原启动、停止和绑定历史。原节点重放已接受的回执不依赖当前 Fleet 清单，也不改动后来的绑定。用户重复停止在绑定释放后仍返回原操作；停止持久化之后出现退出或新绑定的竞态，也不会把已经受理的停止改报成失败，或向新绑定投递旧停止。

此处接通的是 HTTP 接口，节点尚未自动保存和提交证明，用户明确继续／换 Agent 的入口也未接入。默认执行能力仍关闭，后续需验证证明持久化、响应丢失重试与本地新授权接续。

2026-10-23 核验：正常发布列车 39932322218 成功；Hub、stable 与两处受控执行登录均为 `a7b85cc0b`，两节点 10 个关键文件哈希与提交一致，新进程可导入退出证明函数。本次是安装与接口证据，不扩大原生执行域的验收范围。

## 解决方案

### 工作一直留在同一条任务里

一个 Task 保留用户原话、环境、产物和会话历史。切换 Claude / Codex、换上下文、恢复历史都不复制任务。创建它的其他 Agent 没有永久上级权限。

<details>
<summary>技术细节：对象、责任与唯一执行权</summary>

用户是数据所有者和最高控制者；Task 的当前绑定会话是唯一执行责任方。「Owner」不混用这两种含义。

复用当前 `fleet_tasks`、`fleet_operations`、原生会话历史和 inventory。以下是尚待实现的逻辑契约，不要求每项另建表；执行控制只使用一个单调版本 `generation`，不增加平行的控制版本、租约表或 Task 生命周期状态机。现有按 `(repo, issue)` 的 `fleet_leases` 不作为 Task 执行权依据，无仓库 Task 也必须遵循相同控制。

| 逻辑数据 | 必需字段 / 约束 | 权威来源 |
| --- | --- | --- |
| Task | `fid`、既有短码及 T 别名、用户、标题、描述、环境引用、创建时间 | Hub；稳定 ID 不变 |
| 会话关联 | provider、精确 native session ID、worker/node 引用、绑定代次、关联时间、结束关联时间 | Runtime 取得授权后绑定 |
| 执行控制 | 复用 `generation`、`attempt_id`、`execution_owner`、`execution_endpoint`、`cancel_request` 及 operation 引用；绑定保留其原始代次 | Hub 的单一事务写入入口 |
| 原生观测 | provider 原始状态、执行/输入事实、原生请求引用、观测时间、可信度 | 已验证原生事件 / hooks；不能由文本 report 覆盖 |
| 自动运行 | executor（native 或 hub）、规则及修订、是否撤销、下次时间 | 已授权计划；同一计划只有一个执行方 |
| 产物与运行历史 | 沿用已有产物引用、会话历史和操作记录 | 不新增 Agent 回报接口或通用任务事件总线 |
| 用户展示偏好 | 用户＋Task、PIN、PIN 次序、显式归档/收纳偏好 | 用户操作，不由 Agent 状态更新 |

唯一绑定使用现有事务锁和 CAS/唯一约束。`operation` 的幂等键只防同一请求重复，不能防两个不同请求同时启动；启动命令的 `succeeded` 也不证明会话已退出。首版采用不自动过期的持久绑定：超时、心跳缺失、inventory 消失均不释放执行权；旧执行未确认退出，不激活第二个执行域。

**同一事务接受授权：** 锁定 Task，读取已有幂等 operation，校验当前执行是否已退出，再推进 `generation`、记录 `attempt_id` 和执行端点，插入 operation 后一起提交。不得继续以 `acceptDispatch` 与 `InsertFleetOperation` 两个分离事务承担唯一性保证。相同 key 重放返回原操作结果，stop 后也不重新授权；不同 key 遇到已有绑定返回冲突。节点执行 queued operation 时及原生进程创建前都核对授权。当前字段的历史值须经迁移核验，不能因为字段已存在就视为已获授权。

切换流程为：记录切换请求 → 停旧执行域 → 收到匹配绑定的退出证明 → 失效旧绑定 → 激活新绑定。stop 推进授权版本后仍保留旧 attempt 和执行归属，直到它确实退出；退出回执必须匹配该 attempt、端点及原生进程身份，不能用当前 generation 推测已经停止。

同一 native session 不得同时成为两个 Task 的当前绑定。历史只保存引用和必要元数据，不复制厂商完整对话引擎。原生 Subagent / Teams 属于此绑定的原生执行域，不占第二个 Hub 顶层绑定。

旧代次迟到的状态可存入历史；不能覆盖当前观测、消费新请求或清除停止意图。并发点击开始、恢复与换 Agent 返回同一幂等操作结果，或明确冲突；不能偷偷启动第二个。

已有双绑定数据：列出冲突，冻结新的自动启动，保留实际观测；由操作者选择保留会话。不得凭最近更新时间随机选一个、也不得把另一份历史删掉。

</details>

### 列表安静，重要变化看得见

最终列表是「PIN 标题与置顶行 → 无标题普通行 → 更早的会话」。Terminal 保留 iTerm2/tmux 的紧凑列与操作页；Web 保留侧栏＋对话和手机单行列表。运行样式沿用当前安装版本，普通静止行无状态文字。

原型中的两个产品视图展示最终用词、布局和可操作状态；顶端评审栏、场景切换及「示例操作」提示不进入产品。界面中的输入、保存、PIN、历史、停止使用同一份示例 Task 数据，原型不连接真实 Runtime。

**列表投影：** 读取同一 Task 快照，Terminal 与 Web 不分别计算任务生命周期。`running` 是原生事实的只读投影；`needs_input` 是未解决的原生提问/审批或当前会话主动请求；`loop` 是有效重复计划；`pending_start` 是已受理但未见原生执行开始的启动请求。不存在可由多个写入方任意设置的 `task.status=done`。

「待启动」包括首次启动，以及用户明确继续/恢复/切换后等待实际开始的请求。单纯 idle、草稿、已停止且无请求的任务均不显示。成功创建 tmux 窗口或拿到 Session ID 不等于已经执行；以原生 turn/tool 开始证明清除提示。若执行失败，保留失败原因和重试入口在详情，不无限假装排队；需用户修改配置时显示待答提示。

**一个状态槽：** 每行左侧只放一个符号，按需要回答 → 待启动 → 运行 → Loop 选择；没有提示时留空。事实可并存，其余信息进入无障碍名称、hover、Terminal 底部说明或详情，不在行尾重复标记。原生状态、退出原因、机器、PR、单次唤醒时间留在 hover、Terminal 底部说明或详情。单次唤醒不标 Loop；其任务不会因为当前 idle 被自动收入历史。失联沿用淡化样式并明确说明最后观测，不声称已停。

**列表顺序与收纳：** 用户 PIN 的顺序优先；普通列表以最近用户打开/继续或新建顺序展示，原生心跳不刷新排序。一次浏览期间状态事件不改变光标行位置；新行与历史唤醒进入列表时保存当前 Task 和滚动锚点。需要回答、待启动、运行、Loop、有效单次唤醒和观测不明的记录不自动折叠。较旧安静记录沿用现有收纳路径；没有可靠旧记录依据则留在普通列表，不擅自按完成终态划分。搜索包含历史和归档引用；Task 的多次 Session 不拆行。

**操作闭环：**

| 操作 | 成功 | 失败/中断 |
| --- | --- | --- |
| 新任务 | 创建行，显示待启动；首条仍是用户原话 | 文本留在表单；幂等重试，不生成重复 Task |
| 改名 / PIN | 保持同一 Task 和会话 | 回滚该偏好，原位提示；不丢搜索和滚动 |
| 换 Agent / 历史恢复 | 旧绑定退出后才接续；显示待启动 | 旧会话未确认停止则不双跑，可继续重试停止 |
| 自动运行 | 显示生效的计划；仅重复计划加 Loop | 表单解释时间或权限错误，不暗自降级执行 |

| 归档 | 隐藏到历史收纳，仍可搜索 | 活动/计划仍在时提供先停止入口；不以归档代替停止 |

非运行只表示此刻没有工作；不表示成功、失败或结束。成果、错误和下一次执行都有自己的事实来源。

### 停止始终由用户决定

正在工作、等待审批、循环、尚未启动、存在 Subagent、未提交文件或 PR 未合并，都不挡住停止请求。停止之后用户仍可以查看历史和继续工作。

<details>
<summary>技术细节：停止事务、进程归属与竞态</summary>

停止分为两个事实：**不再允许执行**和**远端已停止执行**。第一项由 Hub 持久化确认，第二项必须由 Runtime 证明。只要请求已到达 Hub，节点断网也立即保存停止意图，显示「已受理，远端未确认」；不承诺断网时物理立即停，也不借断网释放旧绑定。操作者连 Hub 也未成功时，界面应显示尚未受理。以下是完整控制闭环的验收要求；已发布和未接线部分以上面的实施进展为准。

1. 验证用户归属，幂等接收 stop；同一事务推进 `generation`、记录停止 operation/`cancel_request`，撤销待启动及未来唤醒/自动恢复授权。先提交再联系节点，不以 `writableAnywhere` 成功作为保存意图的前提。
2. 向当前绑定下发 stop。所有启动入口和已运行进程的自动 turn 提交都检查授权；旧版本请求失效。原生启动和 stop 使用同一节点侧 Task/FID 锁，在放行进程前登记执行域，避免「尚未看到 PID」的间隙被误报为已经停止。
3. Runtime 撤销 Fleet 队列、尚未执行的 native queue 与本任务的原生计划；调用原生停止，关闭顶层会话及可确认归属的原生 Subagents/队友。有界宽限后终止已登记原生组件，重新核验 PID 与出生身份，再记录会话退出回执。已提交至原生端的请求在远端确认前仍列为未确认，不能只删除本地排队记录。
4. 保留历史与文件。停止不等待结果上报、Git 状态、PR、自动清理或 keep；这些只影响独立的后台资源整理。operation 的迟到结果也不能覆盖已撤销的旧启动决定。
5. 之后用户明确继续才取得新的 `generation`/启动授权，不自动恢复已撤销计划。wrapper 自动重试、transfer rollback、旧快照恢复不能自行换取新授权。

**执行入口必须一起收敛：** 只在 wrapper 检查进程启动不够。已运行的 Codex 可以消费 `thread/queue`，Claude 可以从 inbox/原生计划开启下一回合，Fleet Loop 也可直接提交 turn；这些路径不一定再经过 wrapper。当前 `fleet_session_gate.py` 的 `stop` 只中断当前回合，idle/parked 会直接返回成功，不能等同于本方案的 Task stop。

| 入口 | 实现落点 | 共同约束 |
| --- | --- | --- |
| 派发与排队执行 | Hub `fleet_dispatch.go` / `fleet_write.go` / store `fleet.go`；`bin/fleet_control.py`、两种 spawner | Task 行锁内接受授权并记 operation；节点拒绝旧 envelope |
| 原生启动与恢复页重试 | `bin/fleet-session-wrap.sh`、`fleet_native_proc.py` | 创建进程前检查授权、登记执行域；自动重试不签发新授权 |
| 快照与历史恢复 | `bin/fleet-restore.sh`、`fleet-history.sh`、`fleet-task-record.sh` 的 respawn/redo | 自动恢复携带原授权；用户继续经同一事务；历史可读不等于获准执行 |
| Agent 切换与跨机移动 | `bin/fleet-transfer.sh`、`fleet_transfer_source.py`、生成的 `launch.sh`/rollback、`fleet-move.sh`、`fleet-migrate.sh` | 旧执行域退出后才能接续；stop 后目标与回退启动均拒绝旧授权 |
| 停放与定时唤醒 | `bin/fleet_park_wake.py`、`fleet_wake_guard.py`、`fleet_session_gate.py` 的 wake 路径 | seed、待投递记录与计划保留原代次；stop 撤销后不再触发 |
| 当前会话的下一回合 | `bin/fleet_session_gate.py` 的 say/settle/codex_try、`fleet-loop.py` 的直接 turn/inbox 投递；厂商原生计划 | 入口提交和队列消费均受授权约束；远端撤销需确认，主回合结束不代表队列清空 |
| 用户停止 | `bin/fleet-worker-stop.sh` 及 Terminal/Web/CLI 调用方 | 共用持久 stop；区分中断一回合与停止整个 Task；回收工作树独立 |

第一版不增加按时续租/到期释放机制。若以后需要「断网后固定时限内自行停」这一能力，必须另行验证本地 watchdog 和期限机制；不能从 `generation` 推导出这种保证。本轮仅承诺持久撤销、重连后先处理停止、未确认退出前不在别处双跑。

**退出证明的范围（本轮收窄）：** 唯一绑定约束针对顶层 Coding Agent Session。会话退出回执证明 Fleet 管理的顶层原生组件已退出，旧授权与自动恢复已撤销；不证明 Agent 启动过的任意程序、开发服务、外部 CI 或部署都已终止。这些产物不作为释放顶层绑定的前提，不新增 cgroup、平台沙箱或另一套进程编排。本文其余「执行域退出」均按这一范围理解，不能扩大宣传为全机后代清空。

Codex 的专属 app-server 与 TUI 都必须按 PID＋出生身份核验，不能只关闭客户端。Claude 的普通 Subagent 仍由所属原生会话管理；独立 Agent Teams 队友是独立实例，需要按原生身份定点停止，清理失败须明确报告，不能以 lead 退出冒充全部已停。身份不明的进程不按名称、目录猜测或批量终止。

原生持久计划另行验证撤销或恢复隔离：无法确认原生版本会在 resume 时恢复哪些计划，就不自动 resume 原始调度状态；显式继续可启动新原生会话并携带 Task 描述与历史摘要。用户关闭始终可提交，文件与历史保留。只有旧顶层组件确已退出的匹配回执才释放绑定；断网且旧组件仍可能运行时，关闭仍受理，但不假报安全地启动了第二份。

Fleet 不禁止原生 Subagent 写代码；资源归属是 Runtime 的统一能力，不用恢复 Subagent 禁令来绕过问题。任何终止操作不能 kill 共享 tmux server 或兄弟窗口；隔离演练必须验证兄弟任务仍活着。

| 竞态 | 必须成立的结果 |
| --- | --- |
| stop 先提交，队列随后拿到旧启动请求 | 节点校验失败，不启动 |
| 启动已在创建进程，stop 随后到达 | 新进程加入同一执行域并被 stop 捕获；不能漏在注册窗口外 |
| stop 与重复 stop | 同一幂等结果，已停仍成功，不复活 |
| stop 与切换 Agent / rollback | 旧授权失效，目标与源的回退均不再自动启动；显式继续才可重新授权 |
| stop 与已运行会话的 turn 队列 / native 计划 | 撤销待投递和未来计划；已提交原生端的工作纳入执行域停止与确认 |
| 失联节点重连 | 先同步 `generation` 与停止意图并结束旧执行，再考虑恢复；禁止先 restore |
| 旧会话迟到 idle/done/report | 只写历史，不撤销 stop、不改新绑定 |
| 删除网页视图/关闭 iTerm2 | 只离开视图，不隐式停止或删除 |

停止失败区分「Hub 未受理」与「已受理但远端未确认」。前者保留原安排并允许重试；后者未来执行已撤销、远端事实未知。前端不能为了视觉立即消掉 spinner。请求中的 UI 反馈属于操作过程，不是新的 Task 终态。

</details>

**数据迁移：** 增量、幂等、可重跑；先 dry-run 记录用户/Task 数、有效绑定数、旧计划数和冲突数。逐条保留 FID、短码、T 别名、正文、产物、会话原生 ID。旧结果保留为历史记录；旧计划只有可证明仍获授权才生效，否则显示未知并停止新的自动触发。旧驱动器先失去派发权，再迁移成员，绝不双写派发。

**旧节点与运行会话迁移（尚未实施）：** 先发布节点能力声明，表示该版本确已覆盖上述启动、队列、计划、停止及退出证明路径；Hub 只向具备此能力的节点签发受控启动。安装版本号或新 hook 存在不等于旧运行中的 wrapper 已换成新逻辑。旧节点仍可读取历史并接受原有停止请求，但不能被标为已完成新的持久停止闭环。

迁移先逐条核对当前 Task、窗口、native ID 和执行域，建立匹配的绑定；不能只复制历史 `execution_owner` 或用最新心跳推测唯一性。发现双绑定时保留全部证据，暂停该 Task 新启动，由操作者明确保留执行。旧进程无法在原位接入新栅栏时，在原生安全停点结束旧执行并以新 wrapper 接续；尚未取得退出证明就继续保留旧绑定，不强行标记迁移成功。无 Task 归属的历史会话先补齐稳定关联，再进入受控启动路径。

重连节点先读取持久停止意图，取消旧 queued operation、wake seed、native 队列/计划并结束匹配执行域，再允许 restore、transfer 或继续；该顺序不能依赖普通 inventory 到达先后。无法覆盖全部路径的旧节点不得接新的自动启动。新旧 operation 更新器、ID 的 result/closed/reopened 与 reconcile 必须验证绑定，不能清除新停止意图。原 `fleet_ids`/结果历史继续保留，不另建回报或订阅系统。

**切换：** 先影子快照比对，只读；用户级切换写权威，旧新两套只能一套签发执行授权。功能开关只用于迁移，达到删除条件后移除；不永久保留两套 Task 生命周期。

**回退：** 回到兼容读取界面和适配器，不回退 `generation`、停止意图或已产生数据。不能读取新控制栅栏的旧节点拒绝执行授权，而非带风险强行恢复。旧 driver、已停止任务和撤销计划不能因版本回退自动重建。回退后 Task/产物/文件计数不得减少。

**老会话兼容：** 使用现有 `fleet-oldcfg-replay.py` / `fleet-oldcfg-check.sh`。旧工具保留 handler，旧 hook 路径转发或无害退出，新 guard 必须覆盖老入口。COMPONENTS、配置单一列表、安装/卸载清单与文档同时更新。用户约定的「不限制原生 Subagent」替换现有 AGENTS/模板限制，不能只改一份文档。

## 风险与处理

| 会发生什么 | 如何兜住 |
| --- | --- |
| 两个会话同时做同一项工作 | 先建立唯一执行授权与退出证明，未确认旧会话停止不启动第二个 |
| 点停止后任务又自行启动 | 所有启动与自动 turn 入口共用 generation 栅栏，迁移和回退也不绕过 |
| 断网时看起来已停，其实仍在执行 | 分别显示撤销授权和远端确认；不虚构停止成功 |
| 列表太安静，重要问题被藏住 | 需要回答始终可见；活动/计划/待启动不折叠；未知观测可查看 |
| 删除旧编排使老会话坏掉 | 一版本转发与真实旧配置回放；再按调用证据删除 |
| 把原生限制误认为已支持 | 逐 provider/安装版本验证能力；缺口进入详情和发布证据 |

## 还需决策的内容

用户方向已经明确，无需再确认 PIN、历史收纳、轻量提示、无父子/集合或原生 Subagent 解禁。建议默认保留现有原生运行环境和现有观测路径，不新增基础设施。

实施前需要由探测结果决定的是各 Runtime 的可终止执行域方案、各 provider 原生观测与中断接入路径和性能阈值。这些属于实施验证项，不是设计阶段阻止交付的许可门。如果有一项无法满足用户最高停止权，该 Runtime 的对应能力不得宣称上线，方案需明确调整。
