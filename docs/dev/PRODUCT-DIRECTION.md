# Fleet 产品方向与设计原则

## 产品定位

Fleet 专门服务中国大陆的开发者与非开发者，解决顶尖 AI 模型与 Agent 服务在国内接入不便捷的问题。

主要覆盖 OpenAI、Anthropic、Google 等厂商的模型与 Agent 服务，包括 Codex、Claude、Gemini，不绑定单一厂商或产品。

竞争对手是其他中转站提供商。Fleet 通过便捷、可靠的接入，减少用户在账号、网络和运行环境上的负担。

**便捷接入是核心价值；持续在线和灵活使用是配套能力。运行环境与上游服务的稳定性优先于功能扩展。**

对外以服务和产品为主线：先讲给谁用、能做什么、怎么开始，用会话、任务、设备、额度这些用户能感知的词。技术架构、开源与自托管是副线，不作为卖点。

## 设计原则

### 1. 最小核心，原生优先

Fleet 是模型与 Agent 服务的轻量接入和托管层。

模型接入优先兼容官方接口；Agent 接入尽量保留原生界面、命令、工具、技能和授权交互。原生能力能够满足需求时，不另建实现。

不默认改变模型行为，不增加强制工作流。

### 2. 非必要能力全部可选

所有非必要扩展和自定义功能，均不默认安装或启用。

优先使用厂商支持的标准配置、Skills、Plugins、Hooks 和 MCP。扩展由用户主动选择，可独立停用和移除，其失败不应影响核心服务。

不默认注入角色、提示词、工具或工作流。只有标准方式无法满足必要需求时，才增加最小自定义实现。

### 3. 稳定优先，简单优先

先保证可靠接入、持续使用和故障恢复，再增加功能。

减少组件、依赖和故障面，不为未来可能的需求提前堆叠系统。新增厂商或产品应逐一验证，不追求覆盖数量而牺牲稳定性。

明确说明中断与恢复状态，不静默重复执行，不静默替换模型或厂商。

### 4. 完整开源，可检查、可复现

代码、部署架构、配置模板和运维方法均应开源，让第三方能够理解、审查和自行部署。

生产凭据与用户数据不公开。托管服务的价值来自接入便利、稳定运行和持续维护；开源是可检查、可自托管的保证，对外介绍时放在次要位置。

### 5. 透明与安全

公开实际使用的厂商、模型、请求路径、数据流向、权限边界、计量收费规则和重要变更。

用户环境相互隔离，凭据妥善保护，管理权限最小化，敏感操作可追溯。安全承诺必须与实际能力一致。

### 6. 按需使用，按量付费

用户按实际需要选择模型、Agent 和运行资源，费用清楚可查。托管服务也可选择自带订阅：用户接入自己的模型订阅时，只为托管与运行资源付费。

具体价格与资源规格后续确定，不固化在产品方向中。

### 7. 数据由用户掌控

托管环境中的用户文件与会话历史持久保存，由用户按需删除，不擅自清理。

模型接入不以保存请求内容为默认要求，必要的计量信息与内容数据分开处理。

不提供备份，明确说明误删和存储故障可能导致不可恢复的数据损失。持久化不等于备份。

## 产品演进边界

近期优先提供原生 Agent 的云端托管，用户从网页（对话、会话）或终端接入，并按实际需求提供模型接口接入。不重做厂商已有的交互体验。

移除常驻 orchestrator、steward 和 backlog autofill。EPIC 等工作流仅作为可选扩展，不成为使用前提。

长期以稳定 Sandbox 为基础，利用厂商 SDK 和标准扩展提供可选的 Role 与托管执行能力，通过 MCP 供其他 Agent 调用。外部 Agent 负责规划与协作，Fleet 负责可靠执行，不重新引入常驻编排层。

各厂商的授权与地区可用性分别处理，技术接入方式不视为已获许可。国内节点只运行 Codex；Claude 等在地区上不可用的服务只在境外节点运行。

## 设计判断标准

每项新设计都应回答：

- 是否直接改善大陆用户的接入或服务稳定性？
- 是否可以复用官方接口、原生能力或标准扩展？
- 是否必须进入默认核心，还是应当可选？
- 是否增加了不必要的复杂度和维护负担？
- 是否符合开源、透明、安全与用户数据自主的原则？

**本文用于约束后续产品方向，不规定具体技术架构、定价或实现方案。**
