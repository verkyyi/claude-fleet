# Hub 任务抽象简化与编排层减法

设计提案 · T970（当前 brief 显示短码 NV03）· 2026-10-22

本文提出目标模型和迁移边界，尚未改变线上行为。设计文档合并不代表运行时已切换。

## 建议定案

Fleet 只提供任务描述、运行环境、会话接入和任务接口。任务如何拆解、并行、检查、收敛，由当前 Coding Agent 自己决定。

- 取消管家、协调者、EPIC driver 的平台身份、专属权限和常驻工作流。每个 Task 只有一个当前执行会话，对自己的工作负责。
- 取消 Hub 的 Parent–Child 任务模型和定向向 Parent 回报。所有事实写回 Hub；有读取权限的 Worker 都能订阅，不因谁创建任务而获得管理权。
- 默认将复杂工作交给一个 Task 的原生 Agent，用 inline、Subagent 或原生团队处理。Fleet 不限制写代码的 Subagent，不把原生内部 Agent 自动登记成 Hub Task。
- Hub 只保留 Task，不设 EPIC、Batch 或任务集合对象。确有独立环境或交付边界时才创建多个独立 Task，通过直接事件订阅与依赖协作。
- Task 没有「已完成」终态。列表只回答「正在运行吗、之后还会自动运行吗、是否需要我介入」。交付结果保留在事件和产物里。
- 用户随时可以停止自己的任务。停止不以 PR、结果上报、后台任务、子任务或清理工作树为前提。

这里的「唯一 Owner」指唯一执行责任方。数据及停止权仍属于用户；不能把数据所有者从用户改成 Agent。

## 原生能力调查与采用边界

以下依据 2026-10-22 实际读取的官方文档。文档可用不代表 Fleet 安装版本、账号或接入方式已具备该能力，切换前需按能力探测和目标版本验证。

| 能力 | 官方能力与限制 | Fleet 决策 |
| --- | --- | --- |
| Codex Subagents | 支持专门上下文、委派、等待、后续指令和关闭；继承原生权限。当前文档说明本地版本默认启用，具体客户端可见操作有差异 [1] | Task 的内部并行直接使用原生能力，不派生成 Fleet Worker |
| Codex App Server | `thread/status/changed`、`turn/completed` 等通知；`turn/start`、`turn/steer`、`turn/interrupt`；线程订阅是连接上的原生事件流 [2] | 复用现有适配器观察状态、递送消息。不是跨租户、跨厂商、持久化的 Hub 订阅系统 |
| Claude Code Subagents | 单会话内部委派，支持前台/后台、独立上下文和 worktree；由主 Agent 接收结果 [3] | 取消 Fleet 对实现型 Subagent 的禁止；内部父子关系由 Claude 管 |
| Claude Code Agent Teams | 共享任务、消息、多个独立会话；实验能力，默认关闭，并且仍有 team lead [4] | 按需使用，不成为 Fleet 默认依赖；不把原生 team lead 升格为平台协调者 |
| Claude Code 跨会话消息 | `ListAgents`、`SendMessage`；本机下次 idle/退出的一次性通知 `notify_when_idle`，双方需 v2.1.236+；有入站控制、12 小时到期等约束 [5] | 同厂商合适场景直接使用；idle 通知不能当交付成功，也不能替代持久 Hub 订阅 |
| Claude Code Hooks / Channels | Hooks 可观察 Stop、SessionEnd、PermissionRequest、SubagentStart/Stop；Channels 可推事件进正在打开的会话，但仍是 research preview，有认证和组织启用限制 [6][7] | Hooks 是状态源；Channels 是可选投递适配。未满足条件时用显式工具读取，不能假设任意 MCP 通知都能唤醒 Agent |

**研究结论：任务内部编排可以交给原生能力；跨 Codex/Claude、跨机器、会话更换后仍有效的任务事件订阅，仍需要薄的 Hub 存储和接口。** 不为填这个缺口再做一个智能协调者。Claude 原生消息可能启动新回合；因此「接收消息」和「允许自动运行」必须显式区分。

不改写原生协议的状态名，不把 Codex thread 与 Claude Session、turn 混成一个生命周期；不要照搬 Claude Teams 的任务状态到 Hub。

## 最小对象模型

```text
Task（用户的工作与上下文）
  ├─ description + environment + artifacts
  ├─ session history ── 多个历史原生会话
  ├─ current session ── 0 或 1 个当前顶层执行会话
  │                      └─ 原生 Subagents / Teams（Fleet 不编排）
  └─ events + optional wakeup

Task B 的一次执行可依赖 Task A 某个明确的产物事件；两者互不拥有。
```

建议持久化的语义如下，字段名属于提案，不是新增 API 的既成承诺：

| 数据 | 最少内容 | 谁可以改变 |
| --- | --- | --- |
| Task | 稳定 ID、用户、描述、环境引用、产物引用 | 用户；当前会话在授权范围内更新自己的任务 |
| 会话关联 | 原生 provider/session ID、节点、账号环境引用、当前绑定代次、历史绑定 | Runtime 原子绑定；一个 Task 一个当前执行入口 |
| 原生观测 | 原生状态及原始原因、观测时间/来源、连接是否可信 | 原生适配器；Agent 文本报告不能覆盖运行事实 |
| 自动运行意图 | 无，或一次唤醒时间/事件条件；可选重复规则、授权版本 | 用户或已获授权的当前会话；停止立即撤销 |
| 事件 | task ID、会话及绑定代次、事件 ID、任务内序号、类型、时间、内容/产物引用 | Runtime 写事实；当前会话写自身进展与产物；订阅者只读 |

原生 Subagent 不占第二个 Task 顶层绑定。原生 Teams 的内部会话属于一次原生工作运行，保留可查看、可停止的资源归属；不再给每个 teammate 分配 Hub Task Owner。只有用户希望独立管理、独立唤醒时才创建新的 Task。

会话切换采用事务/CAS 和递增绑定代次：停止并确认旧执行域退出后才激活新会话；旧代次迟到事件可归档，不能控制新绑定。历史会话只读，恢复历史必须先取得唯一当前绑定。不能仅靠「数据库里只有一行」宣称没有双跑。

## 状态：一个运行事实，加一个未来运行意图

两种主显示足够，但两个问题不能混成一个布尔值：idle 的循环任务现在没在工作，却还会继续；正在收尾的任务可能已经没有下一次自动运行。

| 原生事实与意图 | 用户看到的主显示 | 附加说明 |
| --- | --- | --- |
| 原生正在执行回合/工具/本次原生后台工作 | 运行中 | 原生状态和当前活动；有定时计划则另显示 |
| 原生 idle，且无唤醒条件 | 非运行中 | 不会自动运行；可继续聊天 |
| 原生 idle，已有定时/事件唤醒 | 非运行中 | 下次时间或等待的明确事件；重复规则可标 Loop |
| 原生等待审批/输入 | 沿用原生事实显示，突出「需要你」 | 展示原生请求和入口；不用另起 blocked→waiting→running 工作流 |
| 原生退出/报错 | 非运行中 | 原生退出原因、最近产物；不推断任务失败或完成 |
| 节点失联、事件过期 | 无法确认运行情况 | 最后观测时间；不能伪装成非运行中 |

最后一行是观测质量提示，不是第三种业务状态。`running` 只能是原生事件的展示投影，不单独存一套可被多方写入的任务状态机。顶层 turn 结束但原生后台工作仍运行时，不应直接显示停了；无法观测后台活动则明确显示观测缺口。

`merged`、测试通过、报告生成属于带证据的事件。`turn/completed` 不等于任务成功，进程退出不等于任务失败，停止不等于任务取消。历史可以搜索「最近交付」与「有产物」，无需「完成后不可再打开」。归档只是隐藏/整理记录；删除另设明确动作，停止不删除文件或历史。

Loop 不再成为角色或第三套状态。如果原生已提供计划，就只读展示并将停止传给原生；只有原生没有跨重启唤醒能力且用户需要时，才由 Hub 保存最小唤醒规则。同一个计划只能有一个执行方，避免原生 cron 和 Hub 同时触发。

## 回报与订阅：统一 Hub，不指定 Parent

概念接口只需要以下几种职责，可复用现有 MCP/HTTP 接口并兼容旧名，不必立即扩张工具数量：

- 读自己的任务及有权限的关联上下文：描述、职责、环境、直接依赖、最近事件。
- 写自己的进展或产物事件。Runtime 自动写运行事实，减少 Agent 忘记 report 导致的假状态。
- 按 Task 和事件类型订阅，凭游标读事件；取消订阅。默认是读取通知，不自动唤醒。
- 用户操作启动、停止、继续以及配置可选唤醒。订阅不授予更改别的 Task 或关闭它的权力。

订阅绑定订阅方 Task，投递时解析其当前会话，不绑定创建者/Parent 窗口。所有有权限的 Worker 都可订阅，不要求任务属于同一集合；跨用户的数据仍需显式授权。创建任务的会话可按需订阅，但不能自动获得永久回报渠道或特殊管理权限。

Hub 先写事件，再通知订阅者；使用现有数据库和传输，不新引入消息中间件。任务内单调游标、事件幂等键、至少一次投递、消费去重即可。重连从游标续读；游标超过保留窗口时返回明确缺口和快照入口，不能悄悄漏消息。暂停的订阅者可保留积压，合并摘要并附原事件引用，避免逐条通知消耗 Agent 回合。

只有用户允许的 `wake_on` 才能因事件启动回合；按任务与规则版本去重，运行中只合并待处理消息，不开第二个顶层会话。任务停止后撤销唤醒，迟到通知可留历史但不能启动 Agent。循环自触发、重复状态消息、订阅者互相回报不得形成无界唤醒。

Codex 用能力已验证的 App Server 投递入口；Claude 优先用适用的原生消息/Channels，条件不足则让 Agent 显式读 Hub。UI 收到事件不等于 Agent 已消费，应分别记录游标/投递回执。Hub 不在线时当前原生工作可继续，事件本地有界暂存；不另启本地协调者或绕过单会话绑定。

## 复杂工作也只是一个 Task

Hub 只有 Task 一种工作对象。一个目标即使需要多阶段、多角色或并行实施，也交给当前 Task 的原生 Agent 管理计划、上下文和内部协作，不另外建立 EPIC、集合页或专门负责协调的 driver。

确有不同运行环境、独立交付或分别操作的需要时，创建多个独立 Task。每个 Task 的描述写清自己的目标、职责、产物接口与直接依赖；通过有权限的任务引用读取相关上下文。它们没有共同父任务、集合 ID、成员关系或聚合状态，创建它们的 Agent 也不因此获得特殊控制权。

整体计划属于复杂 Task 的正文或产物，内部步骤由原生 Agent 展示和管理，不投影成 Hub 的另一层工作对象。独立 Task 可以相互订阅和依赖，但不必先加入任何集合。

**依赖必须依赖产物或明确事件，不能依赖「非运行中」。** 例如 B「基于 API v2 开发界面」等待 A「契约 v2 已发布」的产物事件；A 因额度、审批、退出变 idle 都不能释放 B。事件包含契约版本及来源执行代次，B 的本次唤醒锁定接受的事件，后续 A 重跑不重复启动 B。自动接受条件使用可验证的结构化事实（如指定 PR 已合并），主观质量判断由执行 Agent 或用户负责。

最小依赖能力只支持明确的全满足条件，提交时拒绝环、自依赖和无权限引用；停掉的上游让下游保持未触发，显示缺哪个事件。用户可修改条件或手动启动，解除依赖需留下记录，不通过假装成功解锁。首次实现不做任意表达式、自动重试矩阵、补偿事务或自动拆图。

这是 Task 自身按需配置的确定性唤醒条件，不引入集合、批次调度器或集合生命周期。复杂判断交给普通 Task 的原生 Agent。

## 用户一定能关闭

「停止任务」一次操作撤销未来自动运行、消息唤醒及自动恢复，随后中断当前原生工作并退出本任务执行域。它不问 Agent 是否同意，不等报告，不等 PR，也不因 keep、loop、后台工作或未提交文件拒绝。

1. Hub 先持久化停止意图并推进控制版本；定时器、事件触发、restore 都检查它。停止与已排队启动竞争时，旧版本启动失效。
2. Runtime 使用原生 interrupt/停止入口，给有界退出时间；超时直接终止本任务资源域，不能杀共享 tmux server、共享后台或兄弟任务。
3. 完整包含本次原生 Subagents 和后台命令。资源归属用受控进程域/POD 等机制，不用进程名猜归属；无法可靠隔离的共享后台先不启用。
4. 先停止计算，后做非阻塞整理；保留文件、会话历史和订阅游标。继续由用户显式启动，新绑定代次隔离旧回调。

节点断网时 Hub 仍接受停止并保证不再授权启动，但不能声称已经杀掉远端进程。界面显示「已禁止自动运行，远端停止待确认」；节点重连先执行停止，不能先 restore。需要失联时有界终止的托管场景，用已有 Runtime 租约/watchdog 约束；未验证能力不能承诺立即停止。控制请求 pending 是事实提示，不是阻止用户操作的业务状态。

自动释放空闲资源可以检查未保存工作；用户主动停止绕过这类检查。真正删除文件才需要独立的破坏性操作确认。

## 迁移顺序与删除清单

按可回退切片实施，不把旧状态表换名后继续保留所有逻辑。

| 阶段 | 交付与删除 | 兼容与验收 |
| --- | --- | --- |
| 1. 原生权限与用户停止 | 删除实现型 Subagent 禁令及角色强制提示；用户停止绕过回收门；不再创建管家/协调者身份 | 更新 AGENTS/CLAUDE、安装生成配置、hook 表与测试；旧 hook 路径至少一版无害兼容。已有会话不强制重开 |
| 2. 单一任务会话绑定与状态源 | 原生状态透出、历史会话关联、未来唤醒独立；停止状态写穿终态 | 并发启动/交接/重连验证；先影子对照，按用户或能力切换，不能旧新同时取得执行权 |
| 3. Hub 事件与订阅 | 回报写 Hub；旧 report/await 接口转向相同事件实现；删 Parent 投递、children digest、祖先寻找 | 旧工具仍可调用，但不继续定向 Parent。历史 parent 字段只读；原生消息不可用时显式读取 |
| 4. EPIC 退场 | 复杂工作迁为普通 Task；删除集合对象与入口；停掉 driver 的定时调度 | 已在跑的 driver 不自动杀、不重派成员。切换时停其控制权，保留其原生会话与成果为历史；已有成员作为独立 Task 保留，不重复启动 |
| 5. 删除旧系统 | 删父子关系写路径、角色权限、EPIC ticker、旧终态修复、按角色回收和相关配置项 | 旧工具/hook 过一版兼容后删除；同步 COMPONENTS、文档和安装卸载清单；oldcfg replay 仍须绿 |

旧 succeeded/failed/merged/cancelled 映射为历史事件，不据此推断现在是否运行；旧 next-wake/loop 只有存在有效授权才迁移。旧任务同时有多个会话时不能随便挑一个：停止自动重派，保留实际运行信息，迁移工具列出冲突，处理后再启用唯一绑定。旧 Parent/成员关系只留历史，不重建新的集合对象，也不自动转换成执行依赖。原有总目标与职责说明保留在相应 Task 的描述或历史文档里，需要的执行依赖逐条明确。

回退恢复旧读取/适配接口，不自动复活已停止的任务或重建 driver。停止意图和绑定控制版本必须跨版本生效；无法读新格式的旧 Runtime 不得获得执行租约。历史事件、产物、用户文件不回滚删除。

## 验收清单（未来实现，当前均未声称通过）

- 同时两个启动请求、交接撞上启动、失联后重连：同一 Task 最多一个顶层执行会话，迟到回调不改变新绑定。
- 主会话交替使用 inline、实现型 Subagent、原生 worktree；没有 Fleet 禁令，没有自动创建 Hub 子任务；资源仍记在所属用户和任务下。
- Codex、Claude 各自覆盖执行、idle、审批、报错、退出、后台工作、观测失联；展示原始原因，不从进程在不在猜工作结果。
- 任意两个有权限的 Worker 订阅同一 Task；源会话消失、目标会话更换、重复事件、断线重连均不依赖 Parent，不丢失可重放事件；无权限者无法读写。
- 未授权唤醒的订阅只积累消息；停止后的迟到通知、旧 loop、旧恢复器均不能重启任务；恢复后不重放成重复工作。
- 一个复杂 Task 无 driver 也能做完；Hub 的模型、接口和界面均无任务集合对象；独立 Task 间依赖只在指定版本的产物事件满足后触发一次，idle/失败/关闭不误触发。
- 运行中、审批中、loop、后台 Subagent、未提交文件、PR 未合并均能停止；离线节点如实显示待确认，重连先停止，兄弟任务不受影响。
- 历史「已完成」任务可以继续；用户停掉任务后历史与文件还在；归档与删除没有混入停止。
- 删除项实际不再被安装、不再注入、不再写入；旧会话兼容 replay、迁移重复执行、回退后不复活停止任务均通过。

后续产品实现验收应在隔离测试通过后，对实际发布版本记录两种 Agent 的生产证据；Web 界面按手机 390 与桌面 1440 截图。本文只交设计，不将文档渲染截图当作这些功能已上线的证据。

## 产品方向逐项判断

| 判断 | 本方案回答 |
| --- | --- |
| 改善接入或稳定性？ | 减少常驻 Agent、状态漂移和关不掉的任务；原生交互保持可理解 |
| 复用官方能力？ | 内部编排、Subagents、原生状态与审批直接复用；Fleet 仅保留跨厂商的任务数据与接入适配 |
| 必须默认核心吗？ | Task 描述、环境、唯一绑定、停止是核心；Task 间直接依赖与自动唤醒按需 |
| 增加维护负担吗？ | 不增加协调 Agent、消息中间件和工作流引擎；每批以实际删除旧控制路径为交付条件 |
| 开源、透明、安全、数据自主？ | 原生状态及观测缺口可见；订阅有数据权限；用户最高停止权；历史与文件不随停止删除 |
